# gmp-model — визуализатор планировщика Go (G·M·P) и GC

[English](README.md) · **Русский**

[![Deploy static demo](https://github.com/puddingtonnn/gmp-model/actions/workflows/pages.yml/badge.svg)](https://github.com/puddingtonnn/gmp-model/actions/workflows/pages.yml)

Учебная пиксель-арт визуализация **настоящего** планировщика Go: горутины (G) — гоферы, слоты выполнения (P) — изометрические станции, OS-потоки (M) — тележки с номерами. Плюс сборщик мусора, живая куча, кража работы, блокирующие сисколлы и stop-the-world паузы.

![Скриншот gmp-model](docs/screenshot.png)

## Источник правды — реальный рантайм

Это **не симуляция**. Бэкенд запускает курируемые Go-нагрузки в подпроцессе под [`runtime/trace`](https://pkg.go.dev/runtime/trace), парсит бинарный трейс через [`golang.org/x/exp/trace`](https://pkg.go.dev/golang.org/x/exp/trace) и нормализует его в таймлайн, который фронтенд проигрывает по виртуальным часам. Каждое событие на экране — переходы состояний горутин, привязки P и M, циклы GC, суб-миллисекундные длительности STW, метрики кучи, причины блокировок — взято из настоящего трейса настоящей Go-программы, отработавшей на вашей машине секунды назад.

Там, где трейс чего-то не записывает (состав локальных очередей, кражи, жизненный цикл M), мир реконструирует это честно: реконструкции помечены «(реконстр.)» в тултипах и журнале, а всегда видимая панель **«Допущения»** под легендой перечисляет, что именно условно, а что — факт.

## Возможности

- **Шесть курируемых сценариев** — кража работы, пинг-понг по каналам, давление на GC, блокирующие сисколлы (передача M через sysmon), горячий мьютекс, утечка горутин — каждый трейсится вживую с вашими `GOMAXPROCS` и числом горутин.
- **Настоящие OS-потоки (M).** Трейс несёт id исполняющего потока в каждом событии; тележки паркуются у P-станций и уходят вместе со своей горутиной в блокирующий syscall. Видно, как sysmon забирает P у застрявшего в ядре M.
- **Настоящий GC.** GC-строка в масштабе прогона (полосы конкурентной разметки + STW-тики), heap-бар, покадрово окрашенный фазой GC, и STW-вспышка с честной длительностью паузы (микросекунды, а не растянутая анимация).
- **Журнал событий с причинностью** — все события трейса: кто кого разбудил, сколько ждала/бежала/сидела в ядре, «syscall-возврат без P» и корреляция sysmon-retake — строго из фактов трейса.
- **Зум и пан как на floor796** — колесо приближает до 6×, бирки id перерастеризуются и остаются чёткими.
- **Интерфейс RU/EN** — переключатель в шапке меняет весь UI, включая подписи и журнал.
- **Шарящиеся URL** — сценарий, параметры и момент паузы кодируются в адресную строку.
- **Статик-режим** — запечённая матрица трейсов деплоится на GitHub Pages вообще без бэкенда.

## Сценарии

| Сценарий | Чему учит |
|---|---|
| Кража работы | При `GOMAXPROCS>1` простаивающие P крадут горутины у занятых |
| Каналы (ping-pong) | Кольцо горутин передаёт токены; большинство ждёт на `chan receive` |
| Давление на GC | Быстрые аллокации гонят циклы GC: конкурентная разметка + stop-the-world |
| Блокирующие сисколлы | M блокируется в ядре вместе с G; sysmon отдаёт P другому M |
| Горячий мьютекс | Один `sync.Mutex` сериализует N воркеров при любом числе P |
| Утечка горутин | Горутины вечно ждут канал без писателя; зона Ожидание только растёт |

## Как устроено

```
cmd/workload (подпроцесс, runtime/trace в stdout)
      │  бинарный трейс
      ▼
internal/tracerun  ──►  internal/traceparse  ──►  internal/timeline   ──►  internal/api
  запуск → байты          x/exp/trace → события    доменная модель/DTO       HTTP/JSON
                                                                              │
                                                              web/ (Vite + TypeScript + PixiJS)
                                                    player/ (чистый stateAt(t) + вирт. часы)
                                                    scene/  (изометрический пиксель-мир, зум)
                                                    ui/     (DOM-хром, журнал, i18n)
```

- Трейс снимается в **отдельном подпроцессе** — горутины сервера в него не попадают, `GOMAXPROCS` задаётся на каждый прогон.
- Сценарии пейсят себя CPU-работой (`busyFor`), а не `time.Sleep` — сон паркует горутины и опустошает мир; канальные сценарии без пейсинга генерируют миллионы событий.
- Чистая логика (свёртка состояний, GC-сводка, раскладка, журнал причинности, математика вьюпорта, i18n) покрыта юнит-тестами; визуальный слой проверяют Playwright-харнессы, включая контракт контролов из 26 проверок.

## Быстрый старт

Требуется: **Go 1.25+**, **Node 20+**.

```bash
# бэкенд (терминал 1)
go run ./cmd/server -addr :8085

# фронтенд (терминал 2)
cd web
npm install
GMP_API_TARGET=http://localhost:8085 npm run dev
```

Откройте http://localhost:5173. Каждый «Запустить» записывает свежий трейс выбранного сценария.

### Статическая сборка (без бэкенда)

```bash
go run ./cmd/bake                 # печёт web/public/runs/*.json
cd web
VITE_STATIC=1 npm run build       # фронтенд раздаёт запечённую матрицу
npx vite preview
```

Тот же конвейер деплоится на GitHub Pages при каждом пуше в `main` (`.github/workflows/pages.yml`).

## Тесты

```bash
go test ./...                     # инварианты планировщика (вкл. привязки M), анти-регрессии сценариев
cd web && npx vitest run          # чистая логика: state, GC, layout, причинность, share, viewport, i18n
node scripts/verify-controls.mjs  # Playwright: контракт контролов из 26 проверок (нужны оба сервера)
```

## Заметки о честности

Авторитетный список — панель **«Допущения»** в самом приложении. Кратко: состав очередей и кражи — реконструкции (помечены), время замедлено в тысячи раз, лейн P показывает 6 горутин вместо реальной очереди на 256 слотов, `runnext` не рисуется, GC-фазы sweep/mark-assist и ~25% CPU mark-воркеров опущены, запаркованные M невидимы (трейс не отдаёт их жизненный цикл). Всё остальное — настоящие данные трейса.
